# Grok consumer integration contract (unverified access)

Research for [issue #355](https://github.com/HemSoft/codexbar-ios/issues/355), checked September 23, 2026 EDT. This file records public, unauthenticated evidence only. It is not a setup guide or a claim that CodexBar can sign in to Grok. No account, token, purchase, or linking operation was used.

## What the public endpoints establish

- [xAI OIDC discovery](https://auth.x.ai/.well-known/openid-configuration) advertises authorization-code and device-code grants, S256 PKCE, refresh and revocation, userinfo, public-client token authentication (`none`), and `billing:read`. It does **not** advertise dynamic client registration. Neither a supported grant nor a scope name registers CodexBar or establishes permission to read the Grok consumer billing service.
- The [official Grok CLI reference](https://docs.x.ai/build/cli/reference.md) documents `grok login --device-auth`; its client identity and permissions belong to that application. Do not copy its client ID into CodexBar.
- The [consumer FAQ](https://docs.x.ai/grok/faq.md#usage--limits) describes a shared weekly paid-usage pool, a usage percentage and product breakdown in Settings > Usage, a provider-supplied reset, and separately purchased Extra Usage Credits. These do not establish a constant allowance or a percentage for free-tier activity.
- The deployed [web billing adapter](https://cdn.grok.com/_next/static/chunks/2pusluw6cnma7.js) selects `config.creditUsagePercent`, `currentPeriod.type/start/end`, `productUsage`, `prepaidBalance.val`, `onDemandUsed.val`, `onDemandCap.val`, and a separate `billingPeriodEnd`. It maps period enum values to monthly, weekly, or unspecified. This is evidence of a changing first-party web client, **not** a published third-party API contract or proof of the wire encoding.
- `POST https://grok.com/grok_api_v2.GrokBuildBilling/GetGrokCreditsConfig` with an empty five-byte gRPC-Web message frame, no credentials, and `Content-Type: application/grpc-web+proto` returned HTTP 200 with `grpc-status: 16` and `grpc-message: No credentials presented` on September 23. A POST with an empty HTTP body instead returned `grpc-status: 13` and `Missing request message`. HTTP status alone does not prove a successful RPC. The unauthenticated response included no usage data.
- The [xAI Management API guide](https://docs.x.ai/developers/management-api-guide.md) requires a separate team management key. It does not provide a consumer Grok authorization route. Management and inference credentials are not substitutes for a direct consumer connection.

## Blocking evidence to obtain before exposing a provider

1. Verify an xAI-approved **CodexBar** public client ID, allowed redirect or device-approval flow, least-privilege scopes, and permitted use of the consumer billing service. Discovery does not supply client registration or consumer-service authorization. The developer must resolve this with xAI; the user must not enter client settings, export sessions, or paste credentials.
2. Using authorized development access, prove that the client's bearer token reaches `GetGrokCreditsConfig` for the **selected consumer identity**, without relying on web cookies. Check the actual gRPC status and authenticated identity, account/team scope, response encoding, and contract stability. Record a redacted response fixture and a non-success fixture. Do not store access tokens or personal usage in fixtures.
3. Verify refresh, expiry, revocation, cancellation, account selection, and removal. Confirm that renewal keeps the same subject and that a removed/replaced account cannot restore a credential or cached results from an earlier request.
4. Confirm optional versus present-zero fields, currency units, protobuf seconds/nanos, eligibility, weekly and monthly period boundaries, unsupported periods, and free/no-paid-allowance behavior against the authorized response. The web adapter normalizes missing monetary values to zero; CodexBar must not adopt that fallback for unavailable usage. Product shares are detail rows, not independent meters; the billing-cycle end is not a usage reset.
5. Keep Cursor Models, Other Models, and `cursor.grok-bot-weekly` under Cursor credentials. Never sum a linked subscription grant with Cursor allowances or infer a Cursor subscription from a Grok link. The [Cursor Bot subscription guide](https://cursor.com/help/grok-bot/supergrok.md) says linked grants do not stack.

Once these gates are met, implement guided system-browser setup and account-scoped Keychain storage, then add local-only auth/parser regressions and the iPhone/iPad UI evidence specified in [#355](https://github.com/HemSoft/codexbar-ios/issues/355). Until then, the app must not advertise a Grok connection or fabricate usage. Franz's final live account and quota comparison remains pending; it is not a request to supply development credentials.
